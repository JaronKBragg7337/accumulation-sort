The Accumulation Sort

Every repo on the account, run against one question — not whether it's good, but whether it's the thing you actually want.

The criterion. A system qualifies if it (1) runs without you, (2) is changed by having run, and (3) that change is legible when you come back. Continuation plus memory plus consequence. A screensaver passes the first test and fails the other two.

The narrow version: one accumulating substrate, one world drawn on top of it, one live external constraint feeding it. Two of the three are already joined and running. What is missing is the third — nothing here is fed by anything outside itself.

How this is sorted. Tier judgments live in tiers.json and are applied to whatever the API returns today. Each row carries how far verification went: live system checked means the running database or deployment was inspected, source read means the code was, README read means only the README was, and metadata only means description and size alone.

A README is a claim, not evidence. Descriptions here lag their code badly and in both directions — repos that describe a working system and contain a specification, and repos whose entire description is one word sitting on top of real implementation. So no tier rests on a README unless the writing is the work, which is why every row in the Record tier is legitimately verified that way and no row anywhere else is.

Repos created since the last edit to tiers.json appear under Unsorted rather than being guessed at. Private repos are invisible to the API and are not counted.
